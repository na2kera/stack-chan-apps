## 試験 6: webcam で 10 分ずつ (warm)

`--stats` の出力から転記。RTT は送信開始から応答本文の受信まで (クライアント側)。`latency_ms` は edge 内の解析時間。

| 項目 | RGB565 | JPEG (品質 80) |
| --- | --- | --- |
| 時間 | 12:41:46〜12:52:01 | 12:52:01〜13:02:12 |
| frame 件数 (試行 / 成功) | 1998 / 1998 | 2793 / 2793 |
| 失敗率 | 0 % | 0 % |
| 本文バイト数 | 153,600 (固定) | p50 15,252 / p95 15,588 / max 16,041 |
| frame RTT (ms) | p50 248.2 / p95 306.3 / max 1435.6 | p50 134.8 / p95 185.6 / max 2350.8 |
| `latency_ms` | p50 12 / p95 14 / max 187 | p50 12 / p95 15 / max 22 |
| 送信間隔 (ms、件数) | p50 288.9 / p95 389.5 / max 1471.7 (1920) | p50 204.1 / p95 266.0 / max 2639.8 (2715) |
| fps: 送信間隔 p50 から / 送信間隔 p95 から / 実効 (成功件数 ÷ 撮影時間) | 3.46 / 2.57 / 3.35 | 4.90 / 3.76 / 4.71 |
| warm hello RTT (ms、件数) | p50 98.1 / p95 129.0 / max 154.2 (119) | p50 105.1 / p95 147.6 / max 296.8 (119) |
| candidate RTT (ms、件数) | p50 106.3 / p95 139.7 / max 140.8 (39) | p50 108.9 / p95 157.6 / max 278.8 (39) |
| candidate 本文バイト数 (件数) | p50 15,012 / p95 15,448 / max 15,469 (39) | p50 14,684 / p95 15,082 / max 15,439 (39) |
| candidate の応答形式 | chunked 39 / 39 | chunked 39 / 39 |
| 撮影回数 | 39 (全部 時間切れ・候補あり) | 39 (同) |

- fps の行は fps そのものの p50 / p95 / max ではない。送信開始の間隔 (同じフェーズ内で連続する 2 フレーム) の p50 / p95 を fps に直した値 (p95 は遅い側) と、実効 fps (成功件数 ÷ フレームを回していた時間)。
- RTT のほとんどはネットワーク (東京 → ソウルのコンテナ) と Worker・Durable Object の中継。Worker から見た転送時間 (ログの `ms`) は frame で 55〜80 ms、hello で 40〜45 ms。
- RGB565 は 150 KiB の上りで RTT が約 110 ms 増え、目標 5 fps に届かない。JPEG ならほぼ目標どおり。
- 外れ値 (max 1.4〜2.6 秒) は 10 分に数回。失敗 (3 秒超) は無かった。

gallery への保存 (`--auto-save`、1 回だけ。12:41): `review save` から `photo_ready` まで **2,016 ms** (0.5 秒間隔のポーリング込み。edge の `photo_ready` の `latency_ms` は 1,773)。件数 1 なので参考値。

## 試験 4: frame の Content-Length

最初のデプロイ (Worker は Content-Length を 413 にしか使わない版) で経路を確かめてから、411 / 400 / 413 の検査を入れて Worker だけ再デプロイした (`--containers-rollout=none`)。

| 送り方 | 応答 | どこで返ったか |
| --- | --- | --- |
| 正常 (黒の RGB565 320×240、`Content-Length: 153600`) | 200、`face_count: 0` | edge。**Worker → Durable Object → コンテナで Content-Length は保たれる** |
| chunked (`Transfer-Encoding: chunked`、Content-Length なし) | 200 (edge が処理) | Cloudflare の前段が本文を受けてから Content-Length を付けて Worker に渡している。Worker の 411 には当たらない |
| 本文なし (`curl -X POST`、データなし) | 400 `empty_frame` | edge (Worker には Content-Length 付きで届いた) |
| `Content-Length: abc` / `-1` | 400 (Cloudflare の HTML) | Cloudflare の前段。Worker は呼ばれない (ログなし) |
| 3 MiB の本文 | 413 `frame_too_large` | Worker (`early`)。コンテナは呼ばれない |
| `Content-Length: 3000000` で本文 1 バイト | 10 秒で curl がタイムアウト | Cloudflare の前段が本文を待つ。Worker は呼ばれない |

Worker の 411 / 400 は、外から HTTP/1.1 で送る限り到達しない (前段が先に処理する)。契約を揃えるための保険として残し、`test/proxy.test.ts` で確かめている。

## 試験 7: 撮影中にコンテナが止まる

### (a) rollout

`npx wrangler deploy` (13:03:16) はイメージが同じため「no changes」となり、コンテナの rollout は起きなかった (Worker の新バージョンだけ。撮影は影響なし)。そこで Containers API の `POST …/applications/{id}/rollouts` で同じイメージの rollout (rolling、100 %) を作って強制した (13:04:29)。

| 時刻 (JST) | 出来事 |
| --- | --- |
| 13:04:29 | rollout 作成 |
| 13:05:08〜09 | 旧コンテナが終了。frame 3 件が 500 (`The container is not running` / `just exited`。ライブラリが返す 500) |
| 13:05:09〜15 | frame 2 件がクライアント側で 3 秒タイムアウト (Worker の invocation は `canceled`) |
| 13:05:16.4 | 新コンテナの `server_start` (断は約 7 秒) |
| 13:05:17 | 次の frame が 404 `unknown_session` → 疑似デバイスは ERROR → 撮り直し (新しいセッション) |
| 13:05:17〜 | 正常に撮影を継続 |

frame は試行 1520 / 成功 1514 (500 ×3、タイムアウト ×2、`unknown_session` ×1)。設計 §3.1 のとおり、セッションは復元されず、撮り直しで復帰した。

Worker だけのデプロイ (12:39 と 13:03 の 2 回) では、動いているコンテナとセッションはそのまま残った。

### (b) 疑似デバイスを止めて 5 分待つ

13:16:23 に撮影中の疑似デバイスを一時停止 (SIGSTOP)。コンテナが止まった (13:21:52 に LIVE 0 を確認) 直後に再開した。

- 再開後の最初の要求 (`POST …/timeout`) は `RemoteProtocolError` (keep-alive の接続がサーバー側で閉じられていた)。疑似デバイスは ERROR → 撮り直し。
- 次の hello とセッション開始でコンテナが cold start (約 5 秒) し、その後は 13 回正常に撮影した。frame は 1009 / 1009 成功。
- 期待の「`unknown_session` / 接続断で ERROR → 撮り直し」のうち、接続断の側で復帰した。疑似デバイスは切れた接続で再送しないため。K151 は「新しい接続で 1 回だけ再送」するので、K151 では `unknown_session` 側になるはず (6d で確かめる)。

## 試験 8: Worker の構造化ログ

`wrangler tail` と Workers Observability (Telemetry query API) で確かめた。

- `early`: 401 (`kind` hello / frame)、404 (other)、503 (hello)、413 (frame) を各 1 件確認。
- `forward`: 200 / 400 / 404 / 500 (rollout 中にライブラリが返した 500 を含む) を確認。
- `forward_error` (転送で例外 → 502): 実機では起きなかった。ライブラリは止まったコンテナにも例外ではなく 500 を返す。単体テストで確かめた。
- **欠け**: クライアントが切断してランタイムが invocation を `canceled` にしたリクエスト (7a の 2 件、7b の 1 件) はアクセスログが出ない。応答を返していないので「全応答で 1 件」には反しないが、計数には現れない。Workers Observability の `cf-worker-event` (outcome `canceled`) で数えられる。
- 秘匿性: 03:35〜04:09Z の Observability のイベント 20,000 件 (Worker / コンテナ) と、保存した回の前後を検索し、gallery の URL、`photo_url` / `share_url`、鍵の名前・`Bearer` は 0 件。Worker のログは `event` / `kind` / `status` / `ms` / `colo` だけ。リクエストの URL は Cloudflare 側で `/v1/sessions/REDACTED/frames` と伏せられる。コンテナのログには従来どおり `session_id` / `device_id` が出る。
- `@cloudflare/containers` 自身も `console.error` で `Error proxying request to container <instance id>: …` を出す (rollout 中と cold start の直後)。鍵や URL は含まない。
